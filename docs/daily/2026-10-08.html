🛠️ NewMax（牛马 AI）：本地优先的 AI Agent 工作台
一句话

一个本地优先的工作台，把文件读取、工具调用、Skill、模型切换和自动化工作流组合在电脑上执行。

链接

https://newmax.cc ↗

https://newmax.cc/download ↗

怎么玩

打开官网进入下载页，按 macOS、Windows 或 Linux 选择桌面客户端；安装后先用低风险目录建立一个工作区，再连接自己已有的模型服务或选择可用模型。先让它读取一份不含敏感信息的 Markdown/合同样例，要求它做摘要、提取待办并保存结果；再配置一个简单 Skill，测试“读取文件→调用工具→输出结果”的闭环。确认审批提示、命令白名单和数据导出位置后，再把它接入每日回顾、录音转写或资料整理等重复任务。官网明确把本地文件、工具、工作流和多模型切换作为入口，下载页列出 Apple 芯片与至少 4GB 可用内存等要求，适合先在个人电脑上做小规模验证。

为什么值得关注

它不是单纯聊天窗口，而是把“模型能力留在工作流里”作为产品边界；官网同时强调本地优先、权限审批、命令白名单、数据导出与本地备份。对需要处理合同、简历、技术资料或内部文档的人，真正有价值的是可控的执行链，而不是又一个回答框。今天的推文还给出了注册试用入口线索，但具体额度与版本应以官网实时页面为准。

应用场景
  • 在本机整理文档、录音、会议材料，生成摘要和待办而不先上传整套资料。
  • 把每日复盘、文件归档、周报生成做成可审批的重复工作流。

🛠️ Tencent Octop：可自托管的多用户、多 Agent 助手
一句话

腾讯云开源的自托管 AI 助手平台，单进程提供 Web 控制台、CLI、IM 渠道、定时任务与多 Agent 协作入口。

链接

https://github.com/TencentCloud/Octop ↗

https://github.com/TencentCloud/Octop#readme ↗

怎么玩

先阅读仓库 README 和 SECURITY.md，再准备 Python 3.12+、Node 18+ 与 uv；可以先从源码方式运行，或使用仓库提供的 Docker/安装路径。初始化时让向导创建 SQLite 数据库、JWT 密钥和第一个管理员，随后启动服务并打开 Web 控制台。先只创建一个只读专家，接入一份测试知识库，验证回答、日志和权限边界；再逐步启用第二个专家、定时任务或 IM 渠道。需要浏览器自动化时单独评估 Playwright 依赖，需要多用户部署时再考虑 PostgreSQL。所有云端模型调用都应单独检查数据是否离开本机，不要把“自托管”误解为“模型推理必然本地”。

为什么值得关注

Octop把个人助手、团队协作、知识库、定时执行和外部编码 Agent 放在一个控制面里，并且仓库公开了工具守卫、权限、日志、数据库和插件等工程边界。官方 README 明确列出 Feishu、钉钉、QQ、微信、Telegram、Discord 等渠道以及 ACP/MCP 方向，这比只展示聊天 UI 的项目更接近企业内部 Agent 基础设施；但自托管后的密钥、会话隔离、云模型数据流仍需要自行审计。

应用场景
  • 给小团队部署一个共享的知识库问答、任务分派和定时提醒助手。
  • 将本地专家 Agent 与 Claude Code、OpenCode 等编码工具通过受控接口串联。

🛠️ magpie：统一管理本机 Agent 的模型、上下文和路由
一句话

一个开源桌面/终端工具，把 Codex、Claude Code 等 Agent 的模型选择、Provider、Skill、MCP 与调用状态集中管理。

链接

https://github.com/yetone/magpie ↗

怎么玩

从 GitHub README 选择 macOS 对应版本或源码方式安装，首次启动先让它扫描本机可识别的 Agent；在模型列表里给不同 Agent 指定已有 Provider，不要一上来改动生产配置。打开 Usage → Context，检查系统提示词、工具/MCP、记忆、文件、工具结果和对话各占多少，再对比缓存命中与上下文增速。随后用一个短任务测试 semantic model routing，观察它是否按任务把请求分给合适模型；确认结果后再保存 profile。遇到不确定的 Provider 导入链接，先在界面核对主机、模型与权限范围，再确认写入，避免把密钥或工作区配置误导入错误的 Agent。

为什么值得关注

多 Agent 工作流最容易失控的地方不是模型本身，而是“到底用了谁、带了多少上下文、哪些工具被注入”。magpie 的价值在可视化和集中治理：它不仅能切模型，还把 context window、缓存、工具、记忆与调用质量变成可观察对象。对经常在多个编码 Agent 间切换的人，这类控制面可以帮助定位慢、贵、上下文膨胀和路由错误，而不是凭感觉反复换模型。

应用场景
  • 为不同编码 Agent 配置不同模型，按任务在云模型、本地模型和中转服务间切换。
  • 排查 MCP、记忆或工具结果导致的上下文膨胀与费用增长。

🛠️ Paseo Bots：在本机创建可长期运行的个人 Bot 团队
一句话

Paseo 的开源插件，让每个 Bot 拥有自己的指令、模型、记忆、Skill 和工具，并在独立工作区中协作。

链接

https://github.com/oliexe/paseo-bots ↗

https://paseo.sh/plugins/oliexe/bots ↗

https://github.com/getpaseo/paseo ↗

怎么玩

先安装 Paseo 桌面端或按官方文档安装 CLI，再在插件市场打开 paseo-bots；如果从源码试验，先阅读插件 README 和权限说明。创建第一个 Bot 时只给它一个清晰角色，例如“整理项目 issue”，绑定一个低权限工作区和一个已验证模型；然后创建第二个 Reviewer Bot，让它只读第一个 Bot 的结果。用一件可回滚的小任务测试记忆、状态、路由和工具调用，再观察两个 Bot 是否真的分工而不是重复生成。确认工作区、定时执行和审批策略后，才把它升级成个人助理或小团队；所有插件和模型权限都要按最小范围设置。

为什么值得关注

它把“Bot”从一次性提示词提升成有状态的长期工作单元：每个 Bot 可以有个性、记忆、工具和路由，还能在 Paseo 中组成 Team。这样做的关键不是像聊天机器人一样多一个入口，而是把本机 Agent 的配置、工作区与重复执行能力保留下来。对于不愿把全部工作流迁到云端的人，它提供了一个可观察、可拆分、可逐步加权限的实验路径；但插件生态质量和长期兼容性仍需逐个检查。

应用场景
  • 建立“资料整理 Bot + 审核 Bot”的双人协作式本地工作流。
  • 为不同项目保存独立的记忆、工具权限与定时任务。

🛠️ Huashu Design：用 HTML 原生方式产出原型、幻灯片和动画
一句话

面向 Claude Code、Cursor、Codex 等 Agent 的开源设计 Skill，覆盖高保真交互原型、HTML 幻灯片、动效和可视化。

链接

https://github.com/alchaincyf/huashu-design ↗

https://github.com/alchaincyf/huashu-skills ↗

怎么玩

先执行仓库 README 给出的安装方式，例如在支持 Agent Skills 的环境中运行 npx skills add alchaincyf/huashu-design；安装前先通读 SKILL.md，明确它适合原型、演示、动画和信息图，不是生产级网站后端。准备一份真实但不敏感的品牌色、Logo 或产品截图，给 Agent 一个明确交付物，例如“做一页可点击的移动端 onboarding 原型”；让它先输出 HTML，再在浏览器中检查交互、移动端布局和可访问性。需要动画时再要求导出 MP4/GIF，并按 README 的依赖与音频要求验证成品。每次只改一个设计变量，保留上一版 HTML，便于比较而不是让 Agent 无限重写。

为什么值得关注

它把“设计交付”从静态图片提示词拉回可检查的 HTML：原型可以点击，幻灯片可以在浏览器演示，动画可以由时间轴和参数驱动。仓库还把设计哲学、评审维度和资产目录写进 Skill，减少 Agent 只堆渐变和卡片的默认审美。对产品经理、独立开发者和需要快速验证方案的人，HTML 既是产物也是审查界面；不过复杂项目仍应把它当设计探索工具，而不是替代生产前端工程。

应用场景
  • 快速做产品流程原型，让团队直接点击和比较多个方案。
  • 从一句话生成可演示的发布动画、信息图或网页幻灯片。

🛠️ EmbeddingGemma 2：面向端侧 RAG 的统一多模态嵌入模型
一句话

Google DeepMind 的 740M 参数开放模型，把文本、代码、图像、视频和音频映射到同一个 768 维向量空间。

链接

https://ai.google.dev/gemma/docs/embeddinggemma/model_card_2 ↗

https://developers.googleblog.com/embeddinggemma-2-the-developer-guide ↗

https://huggingface.co/google/embeddinggemma-2 ↗

怎么玩

先读模型卡，确认 Apache 2.0 许可、8,192 token 上下文、输入模态和 MRL 降维选项；本地实验可以安装 pip install -U "sentence-transformers[image,audio,video]" transformers。先只加载文本/代码配置，用公开的 Markdown、代码片段和问题构造一个小型检索集，分别用 SearchQuery 与 Document 的 prompt_name 生成向量，再测 top-k 命中。随后逐步加入图片或短音频，检查跨模态查询是否真的能找到对应文档，而不是只看相似度数字。根据设备内存选择 270M 文本、包含视觉/音频的模块组合，并把 768d、512d、256d 的存储和召回效果做一次对照；生产前再评估量化、隐私和敏感内容过滤。

为什么值得关注

它把端侧 RAG 的拼装成本压低了：不必为文本、图像和音频分别维护完全不兼容的向量空间，统一表示让跨模态检索有了更直接的工程路径。模型卡还给出模块化参数规模与 128/256/512 维截断方案，意味着可以按设备内存和向量库成本取舍。对于个人知识库、手机端搜索和本地多模态资料管理，这是比“再换一个聊天模型”更基础、也更可能长期复用的一层能力。

应用场景
  • 在本地文件库中同时检索文字、代码、截图、视频片段和录音。
  • 为隐私敏感的端侧应用搭建轻量级多模态 RAG 或分类器。

解读

这代表聊天产品的竞争单位从“生成一段文本”向“生成一个临时应用界面”移动。用户不必先知道应该打开哪个工具，系统可以根据问题即时构造一个可点、可调、可继续操作的界面；这对预算计算、学习演示、数据解释和流程规划尤其自然。开发者需要关注的不是 UI 看起来是否漂亮，而是生成的状态、计算逻辑、数据引用和权限是否可验证。交互界面越强，错误也越可能被用户误操作放大，因此审计、可回退和结构化输出会成为新一层产品要求。
