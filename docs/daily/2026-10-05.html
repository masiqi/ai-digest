🛠️ Paseo：桌面、手机、Web、CLI 的多 Agent 控制台
一句话

Paseo 是一个开源的编码 Agent 运行环境，用本机守护进程统一管理 Agent，并提供桌面、手机、Web 与 CLI 客户端远程驱动工作区、终端和任务。

链接

https://github.com/getpaseo/paseo ↗

怎么玩

先从 https://paseo.sh/download 下载桌面版，打开后让它启动内置 daemon；然后在 Settings → 你的主机 → Pair Device 里配对手机。使用前要在本机先装好至少一个 provider CLI，例如 Claude Code、Codex 或 OpenCode，并确保其凭据已经可用。想走命令行，可执行 `npm install -g @getpaseo/cli paseo`；想在服务器试验，可用官方 Docker 镜像并映射 6767 端口。创建一个工作区，分别启动两个 Agent，让一个负责实现、另一个负责测试或审查，再从手机观察状态、切换会话和处理需要人工确认的步骤。不要把它当模型服务：Paseo 管理的是已有 Agent CLI，不会替你提供模型账号。

为什么值得关注

它把“多 Agent 编排”从 tmux 和 SSH 的个人技巧，推进成跨设备的产品界面。开源仓库同时包含 daemon、桌面端、移动端、Web、CLI 与加密 relay，说明重点不只是聊天窗口，而是工作区、远程连接、Git worktree 和多提供商协作的组合。对需要长时间跑编码任务的人，手机端查看和干预比反复登录服务器更实用；但它仍继承底层 Agent CLI 的权限和安全边界，部署前应审查 relay、沙箱与凭据配置。

应用场景
  • 在家用 Mac 上启动多个编码 Agent，出门后用手机查看构建、测试和待确认操作。
  • 给一个 Agent 派实现任务，给另一个 Agent 派代码审查或回归测试，集中在同一工作区管理结果。

🛠️ Strata：8GB+ NVIDIA 显卡本地运行 125B Qwen3.8-Flash-Next
一句话

Strata 是针对 Qwen3.8-Flash-Next 的专用推理引擎与本地 API/UI，利用稀疏 MoE、显卡、内存和磁盘协同，把超大模型带到消费级 NVIDIA 硬件。

链接

https://github.com/Niko1221/Strata ↗

怎么玩

准备 Windows 或 Linux 机器、NVIDIA GPU、至少 8GB 显存；更贴近仓库推荐体验的是 12–24GB 显存加 64GB RAM。克隆仓库后按 README 的一键安装脚本下载模型和运行时，启动本地服务，再用它提供的 Web UI 对话；也可以把 OpenAI 兼容 localhost API 接到 Open WebUI、自己的脚本或编码 Agent。先从短上下文、低并发开始，观察显存、内存、磁盘读取和首 token 延迟，再逐步增加上下文。原始推文称 12GB 显存可运行，但这不等于所有 12GB 机器都能流畅运行；实际速度会受 RAM、NVMe、CUDA、量化格式和 KV cache 限制，建议先按仓库的兼容配置做小规模测试。

为什么值得关注

Qwen 官方资料显示 Flash-Next 是 125B 主模型、每 token 激活约 6B 参数的稀疏 MoE，并带有额外的 n-gram 参数；Strata 把这类“总参数很大、每次只算一小部分”的结构落到消费级硬件上。它不是通用推理框架，而是围绕单一模型深度优化，因此更容易在目标设备上做内存分层和投机解码，也更容易暴露专用引擎的局限。对本地 AI 来说，真正的门槛从“能不能装下权重”转向整机内存层级、上下文策略和持续吞吐。

应用场景
  • 在不上传敏感代码或文档的情况下，测试本地长上下文和 Agent 工具调用。
  • 用同一个本地 API 给桌面聊天、脚本和内部原型提供模型服务，比较云端成本与本地延迟。

链接

https://www.localmaxxing.com/en ↗

它把“某模型很快”的营销说法拆成可比较的硬件、引擎、量化和上下文条件。官网明确说明数字来自社区提交的真实硬件运行，而不是厂商速度测试；平台还把模型、硬件、基准评测、市场和租赁入口放在一起。对本地部署而言，这种可按条件过滤的经验数据库比一条脱离环境的 token/s 宣传更有用，也能帮助用户判断是换模型、换量化，还是换推理引擎。

应用场景
  • 为本地编码 Agent 选择能够满足交互延迟和上下文要求的模型配置。
  • 购买或升级显卡前，用相同模型与量化的社区记录估算实际收益。

🛠️ LiteLLM Lens：让 Agent 轨迹进入可调查的闭环
一句话

LiteLLM Lens 是 LiteLLM 体系内的早期访问功能，用 AI Agent 分析生产轨迹，聚合重复失败并把调查结论链接回原始 trace。

链接

https://docs.litellm.ai/docs/proxy/lens ↗

怎么玩

先阅读官方 Lens 文档并申请 early access；部署 Lens 及 LiteLLM proxy，按部署文档准备 ClickHouse 作为 trace 存储和 PostgreSQL 作为调查结果与设置存储，再接入官方 first-trace 或 coding-agent 指南。先只记录一个可控的 Claude Code 或 Codex 工作流，明确“什么算成功”，让少量真实 trace 进入系统；然后在 Lens → Traces 检查单次运行，再在 Investigations 中按需或定时调查一组运行。把 Lens 的发现当作待验证假设：回到原始 trace 复现问题，再用测试或人工审查确认改动，不要因为聚类结果看起来合理就自动修改生产系统。涉及用户数据时，配置最小权限的读取账号、脱敏与保留策略。

为什么值得关注

许多 Agent 团队已经能收集日志，却无法从海量轨迹中找出反复出现的失败模式。Lens 的差异在于把 trace 检索、失败调查、相似问题分组和证据链接放到同一个工作流里，且官方路径支持 Claude Code、Codex 等编码会话。它仍是 early access，不是“自动修复生产”的按钮；观测范围也取决于你实际埋点，模型请求本身不会自动覆盖所有浏览器动作、检索和外部业务结果。

应用场景
  • 对编码 Agent 的失败运行按工具调用、测试结果和任务类型聚类，定位最常见的失误。
  • 为客服、研究或自动化 Agent 建立“期望行为—轨迹—调查—回归测试”的质量循环。
